1. The Big Picture

The HighRadius frontend is built across four Git repositories. Three are plain single repos. One is a monorepo. They connect in a strict chain — each one depends on the one to its left, never the other way around.

Only ui-nexus is a monorepo untitled-ui, next-js-boilerplate, and record-to-report are all standard single Git repositories. Only ui-nexus uses Turborepo, has multiple packages, and publishes multiple npm artifacts.

3. Each Repo Explained

3.1 untitled-ui  Single Repo

What it is: A plain single Git repository that holds a copy of the Untitled UI React component library source code, exactly as it was released upstream. No modifications, ever.

What it publishes: One npm package — @highradius/untitledui — to the private HighRadius npm registry. It exports all React components, icons, and CVA variant configs.

Why we keep it unmodified: If we change files here, upgrading to a new Untitled UI release becomes painful — we have to diff our changes against the new version. By keeping it clean, an upgrade is just: pull new source → bump version → publish.

Rule: no one imports @highradius/untitledui directly Only the ui-nexus base-components package is allowed to import from it. If you need a UI component, import from @highradius/ui instead.

What's inside

untitled-ui/
├── src/
│   ├── components/      ← all Untitled UI React components (unmodified)
│   ├── icons/           ← SVG-in-React icon set (unmodified)
│   └── variants/        ← CVA variant configs (unmodified)
├── package.json         ← name: "@highradius/untitledui"
└── .github/workflows/
    └── publish.yml      ← on tag: build → publish to private npm

When do you work here?

  • When Untitled UI ships a new release and you need to update the vendored copy.
  • When you need to verify what components are exported before using them in ui-nexus.
  • You never add business logic, styling overrides, or HiRa-specific code here.

3.2 ui-nexus  Monorepo — the only one

What it is: The central platform monorepo. It contains all shared configurations, the HiRa design system (base-components), and platform-level feature packages. Managed with Turborepo and pnpm workspaces.

What it publishes: 13 versioned npm packages to the private registry. Config packages are used by all repos (including the boilerplate). Runtime packages are installed by product apps like record-to-report.

The two types of packages it publishes

TypePackagesWho installs them
Config packages
(devDependencies)		 @hr/tsconfig, @hr/tailwind-config, @hr/oxlint-config, @hr/commitlint-config, @hr/lefthook-config next-js-boilerplate, record-to-report, and any future product repo
Runtime packages
(dependencies)		 @hr/ui, @hr/tokens, @hr/icons, @hr/shell, @hr/data-table, @hr/forms, @hr/state, @hr/api-client Product apps (record-to-report, future products)

The base-components layer — where HiRa design lives

This is the only place in the entire ecosystem where @highradius/untitledui is imported. It wraps each Untitled UI component with HighRadius brand colors, sizes, and states using CVA, then re-exports them as @highradius/ui. 

// packages/base-components/src/button.tsx
import { Button as UntitledButton } from '@highradius/untitledui';
import { cva } from 'class-variance-authority';

const buttonVariants = cva('', {
  variants: {
    hiraVariant: {
      brand: 'bg-hira-600 hover:bg-hira-700 text-white',
    },
  },
});

export function Button({ hiraVariant, className, ...props }) {
  return (
    <UntitledButton
      className={buttonVariants({ hiraVariant })}
      {...props}
    />
  );
}

Build order inside ui-nexus

Turborepo enforces this order automatically:

config packages → @hr/tokens → base-components → @hr/ui → platform packages
(tsconfig, tailwind, oxlint)     (design tokens)   (HiRa wrap)  (shell, data-table, forms…)

When do you work here?

  • Adding or updating a HiRa-branded component variant (base-components).
  • Updating shared lint, TypeScript, or Tailwind rules (config packages).
  • Building a new platform-level feature: data grid, form system, shell layout.
  • Never add product-specific business logic here.

3.3 next-js-boilerplate  Single Repo · GitHub Template

What it is: A single-repo Next.js 15 starter that is published as a GitHub template repository. It is not a monorepo — it has one package.json at the root. New product apps are created by clicking "Use this template" on GitHub (or gh repo create --template).

What it publishes: Nothing to npm. It is a template, not a package. When a team bootstraps a new product, they get a ready-to-run Next.js repo.

How it connects to ui-nexus

The boilerplate pulls the five config packages from ui-nexus as devDependencies. This means all linting, TypeScript, Tailwind, and git hook rules come from ui-nexus — one source of truth. When ui-nexus updates a config package, all repos that inherited the boilerplate just run npm update (or wait for Dependabot to open a PR). 

// next-js-boilerplate/package.json
{
  "devDependencies": {
    "@highradius/tsconfig":          "^2.1.0",
    "@highradius/tailwind-config":   "^1.3.0",
    "@highradius/oxlint-config":     "^1.2.0",
    "@highradius/commitlint-config": "^1.1.0",
    "@highradius/lefthook-config":   "^1.0.0"
  }
}

What is pre-wired

  • Next.js 15 with App Router and output: standalone
  • Wattpm Gateway — Fastify process on port 3000 (auth, proxy, Redis)
  • T3 Env — type-safe environment variables with Zod
  • Playwright — E2E test setup pre-wired to the Wattpm Gateway URL
  • GitHub Actions — lint → typecheck → test → build → deploy pipeline
  • Docker Compose — local dev stack (app + gateway + Redis + mock OIDC)
  • All ui-nexus config packages already installed and configured
How record-to-report was bootstrapped The R2R team cloned this template, renamed the repo, and only had to add product-specific pages and install the ui-nexus runtime packages (@hr/shell, @hr/ui, @hr/data-table, etc.). Everything else — tooling, gateway, CI/CD, Docker — was already working.

When do you work here?

  • Updating the starter template for all future products (platform team).
  • Adding new default tools that every HighRadius product should have.
  • You do not add product features here. This is a template, not a live app.

3.4 record-to-report  Single Repo · Product App

What it is: A single-repo Next.js product app that ships to real users. It was bootstrapped from next-js-boilerplate. Wattpm Gateway (port 3000, public) sits in front of Next.js Standalone (port 3001, internal). It consumes all ui-nexus runtime packages.

What it ships: The live Record to Report financial application — reconciliation, journal entry, close management pages.

Ownership split — platform team vs R2R team

Two teams co-own this repo. CODEOWNERS enforces who reviews what:

A typical product page

// app/(finance)/reconciliation/page.tsx  — owned by R2R team
import { HighradiusPlatformShell, DataTable } from '@highradius/shell';
import { fetchReconciliationData } from './data/reconciliation';
import { ReconciliationToolbar } from './components/ReconciliationToolbar';

export default async function ReconciliationPage() {
  const data = await fetchReconciliationData();

  return (
    <HighradiusPlatformShell
      rbacRequiredRole="finance_admin"
      headerSlot={<ReconciliationToolbar />}
    >
      <DataTable data={data} />
    </HighradiusPlatformShell>
  );
}

When do you work here?

  • Building finance features: reconciliation, journal entry, close management.
  • Adding Playwright E2E tests for financial workflows.
  • Updating monitoring checks (Checkly).
  • You do not change the Wattpm Gateway or layout.tsx without platform team review.

4. The 5 Rules Every Developer Must Know

1
Only base-components imports @highradius/untitledui No other file in any repo imports from @highradius/untitledui. Always import UI components from @highradius/ui. Enforced by Turborepo boundary rules and Knip.
2
One-way dependency chain — no reverse imports untitled-ui ← ui-nexus ← product apps. Nothing flows backwards. A product app cannot be imported by ui-nexus. A config package cannot import a runtime package.
3
ui-nexus is the only monorepo untitled-ui, next-js-boilerplate, and record-to-report are all single repos. Do not create workspaces, Turborepo configs, or pnpm-workspace.yaml in them.
4
The Gateway owns authentication — Next.js Standalone never sees raw tokens Wattpm validates OIDC tokens, caches RBAC in Redis, and passes user context as headers. The Next.js server only receives requests that Wattpm has already approved. Auth tokens must never appear in browser JS.
5
Platform shell is mandatory in every product layout HighradiusPlatformShell from @highradius/shell must wrap every product page. It provides security (Arcjet), error tracking (Sentry), analytics (PostHog), RBAC enforcement, and i18n. It cannot be removed — CODEOWNERS prevents it.

6. How a Component Travels from untitled-ui to Your Page

Here is the full journey a single component takes — from the upstream Untitled UI source to a rendered pixel in a user's browser.

1
untitled-ui repo — holds src/components/Button.tsx, the original Untitled UI component. No changes. Publishes it inside @highradius/untitledui.
2
ui-nexus / base-components — imports Button from @highradius/untitledui. Wraps it with HiRa brand colors and size tokens using CVA. Re-exports as the Button in @highradius/base-components (internal package, not published directly).
3
ui-nexus / @hr/ui — re-exports everything from base-components as the public, stable API. This is the package product teams install: npm install @highradius/ui.
4
ui-nexus / @hr/shell — imports @hr/ui components to build the platform layout (sidebar, topbar). Published as @highradius/shell.
5
record-to-report — installs @highradius/shell and @highradius/ui. The product page wraps content in HighradiusPlatformShell (from @hr/shell) and imports individual components from @highradius/ui for the page body.
6
Browser — Wattpm Gateway proxies the authenticated request to Next.js Standalone. React renders the component tree. The user sees a fully branded, HiRa-styled button, built on top of Untitled UI's foundation. 
untitled-ui/Button.tsx
  → @highradius/untitledui (published)
    → ui-nexus/base-components/button.tsx (HiRa variants added)
      → @highradius/ui (published, public API)
        → @highradius/shell (platform layout)
          → record-to-report/app/layout.tsx + page components
            → Wattpm Gateway → Browser
